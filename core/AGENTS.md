# Lotus Agent 工作协议

> 版本：v1.3。本文件是 Lotus 的全局顶层宪法，只保存所有任务都应常驻的约束、路由和交付契约。项目特定约束放在项目根目录的 `AGENTS.md` 或 `.agents/rules/` 中；具体技能流程放在对应 `SKILL.md` 中按需读取。
> 本协议由 [Lotus](https://github.com/Bronc-X/Lotus) 维护，兼容 Claude Code / Codex / Antigravity / Gemini CLI / OpenCode / Cursor / Windsurf / Copilot / Aider。

## 优先级

在宿主系统规则允许范围内，按以下顺序收敛上下文：

1. 用户当前明确要求。
2. 当前项目的 `AGENTS.md`、`.agents/rules/`、技术栈和测试约定。
3. 本全局协议。
4. 被用户点名或语义命中的 skill。

只读取完成当前任务所需的规则；不要把完整手册、长技能列表或无关流程塞进上下文。

## 四条护栏

1. **先想清楚，再写代码**：先确认目标、边界、关键假设和成功标准；发现歧义时显式指出，关键事实不清楚就澄清或先验证。
2. **简单优先**：只实现当前问题需要的最小方案；不为单次场景提前抽象，不预埋未提出的配置、层级和开关。
3. **手术式修改**：只改与目标直接相关的文件、函数和行；不借机重构、改风格、升级依赖或清理无关历史残留。
4. **目标驱动闭环**：把任务先变成可验证目标和明确契约；Bug 先复现再定位再修复再验证，新功能先定义成功标准再实现，重构必须证明前后行为一致。

## 默认执行

除非任务极小、风险极低，否则按这个节奏推进：

1. 用一句话改写目标、边界、交付契约和成功标准。
2. 读取最小必要上下文，优先使用项目现有模式。
3. 选最小可行方案并锁定修改范围。
4. 实施后用测试、构建、运行结果、浏览器检查或明确的静态检查闭环。

## Agentic Coding 契约

非平凡任务开始前，先形成轻量契约。契约不是让用户盯实现细节，而是让 AI 对最终结果负责：

- **目标**：用户可观察到什么变化，什么算完成。
- **边界**：哪些文件、模块、行为在范围内；哪些明确不碰。
- **做法**：准备用哪类最小方案，不展开无关重构。
- **验收**：用什么测试、构建、复现步骤、静态检查或人工路径证明完成。
- **失败方式**：如果无法完成，要给出卡点、证据和下一步，而不是静默失败。

用户关注目标和契约；AI 负责拆解怎么做、实际执行和验证闭环。

## Debug 规则

Debug 的默认目标不是“看起来修好了”，而是把问题压缩到最小可解释位置。

1. **先定位最小位置**：从症状出发，沿入口、调用链、数据形状、状态变化和副作用逐层收敛；最终补丁应落在能解释问题的最小文件、函数或分支上。
2. **先拆原因再动手**：修复前先拆出原因树。若某一层仍有“不知道为什么”，继续向下拆；不要带着关键未知直接写补丁。
3. **证据优先**：每个主要判断都要有日志、测试、代码路径、状态快照、网络响应、构建错误或可复现步骤支撑。
4. **最小补丁**：只修改根因所在的最小范围；若补丁超过三个文件、跨服务边界、涉及权限/安全/数据损坏，升级为完整调查流程。
5. **回归验证**：用原始复现路径证明症状消失，再用便宜但可信的检查证明没有打破相邻行为。

## 代码语言优先

能写进代码、类型、测试、schema、断言、路由表或配置契约的规则，不只写在自然语言说明里。自然语言用于说明意图和索引证据，代码内部要承载真正的约束，减少转述损失。

优先选择：

- 用类型、接口、枚举、schema 表达数据边界。
- 用测试、快照、fixture、contract check 表达预期行为。
- 用清晰函数名、局部变量名和小范围控制流表达业务规则。
- 用项目已有 helper 和模式表达约定，而不是另起一套口头规则。

## 意图路由

- **小 Bug / 单一症状 / 明确局部异常**：默认使用 `/mini-investigate`。读取对应 `SKILL.md`，按“复现 -> 原因树 -> 证据链 -> 最小定位 -> 最小修复 -> 回归验证”执行。默认只动一个文件；超过三个文件、涉及安全/权限/数据损坏/跨服务边界，升级为更完整的调查流程。
- **复杂 Bug / 构建失败 / 根因不明**：先复现并列出假设，使用 `/debugging-strategies` 或 `/investigate`；不要猜一个修一个。
- **大型新功能 / 核心流程重写**：先写成功标准和实施边界；必要时做产品和工程方案评审，并在大范围编码前让用户确认。
- **前端页面、视觉或交互工作**：读取项目设计规则；按需使用 `/frontend-design`、`/taste-skill` 或设计审查流程；完成后用浏览器检查关键视口和交互。
- **重构**：先列出不可改变的行为，小步修改，小步验证；不改变业务逻辑。
- **安全、权限、依赖、合规风险**：使用 `/security-auditor` 或更严格的审计流程，不用普通 Bug 流程草率处理。
- **Ship / review / QA / deploy**：用户明确要求时使用对应宿主或 gstack skill；官方 gstack 能力以上游 `garrytan/gstack` 为真源。

## Skill 策略

- 用户点名 `$skill`、`/skill` 或任务语义明显命中时，先读取该 skill 的 `SKILL.md`，只执行与当前任务相关的部分。
- Lotus 顶层协议不维护完整 skill 清单；slash skill 本体必须存在于宿主全局 skills 目录，例如 Codex 的 `~/.codex/skills` 或 Claude Code 的 `~/.claude/skills`。
- `/mini-investigate` 是小型 Bug 的默认入口：查真实原因、用证据证明、做最小修复、验证原症状消失。
- `btw` / `@btw` 是会话内旁路快问：只做 3-5 句话的简短回答，不改文件，回答后回到主线。
- `loop` / `@loop` 是会话内轮询：解析间隔和任务，说明当前会话关闭后停止；有副作用的动作需先确认。

## 质量门禁

按风险选择最便宜但可信的验证方式。提交前至少自检：

- 没有新增静默失败；错误要有可见反馈或可诊断路径。
- loading、loaded、error、empty 等状态在用户路径上闭环。
- 按钮、表单、异步动作有明确反馈，避免重复提交。
- 没有新增 `console.log`、`TODO`、`FIXME`、硬编码本机路径或泄露密钥。
- TypeScript 项目避免新增 `any`；接口和状态形状保持清楚。
- UI 改动要检查响应式、可访问性、文本溢出和交互状态。

验证命令和项目细节以当前项目规则为准；Node 项目通常优先尝试 `npm run build`，有测试则跑相关测试。
