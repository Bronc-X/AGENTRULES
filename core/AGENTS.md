# GStack 工程协议 v1.1

> 本文件是所有项目共享的通用工作流规则与质量标准。
> 项目特定约束（技术栈、设计语言、AI 引擎等）请写在项目根目录的 `AGENTS.md` 或 `.agents/rules/` 中。
> 本文件由 [Lotus](https://github.com/Bronc-X/Lotus) 仓库维护，兼容 Claude Code / Codex / Antigravity / Gemini CLI / OpenCode / Cursor / Windsurf / Copilot / Aider。

## 四条执行护栏

这四条是 Lotus 的顶层约束，优先级高于后面的场景路由、技能说明和实现细节。目标只有一个：降低幻觉、减少乱改、压住目标漂移。

1. **先想清楚，再写代码（Think Before Coding）**
   - 先确认目标、边界、假设、成功标准，再开始实现
   - 发现歧义时必须显式指出，不能静默选一种解释
   - 如果存在更简单方案，要主动提出，不能为了“显得聪明”堆复杂度
   - 如果关键事实不清楚，就停下来澄清，不准用猜测填空
2. **简单优先（Simplicity First）**
   - 只写解决当前问题所需的最小代码
   - 不为单次使用场景提前抽象，不为未提出的未来需求预埋配置
   - 不引入“也许以后用得上”的层级、开关、框架和包装器
   - 200 行能解决的问题，不要写成 500 行
3. **手术式修改（Surgical Changes）**
   - 只改与当前目标直接相关的文件、函数和行
   - 不借机清理无关代码，不顺手重构，不因为看不顺眼就全面改风格
   - 你的改动导致的残留必须清掉，你没造成的历史残留只提示，不擅自处理
   - 每一处变更都应能追溯到“用户要求”或“验证需要”
4. **目标驱动执行（Goal-Driven Execution）**
   - 先把任务改写成可验证的目标，再进入实现
   - Bug：先复现，再修复，再验证
   - 新功能：先定义成功标准，再实现，再做构建/测试/交互验证
   - 重构：前后行为必须一致，用测试、构建或运行结果证明

## 核心原则

1. **执行思维，而非脚本** — 价值在于审查标准、质量门禁和认知模式，不在于特定平台命令
2. **平台原生工具替代** — 在每个 AI 编码工具中使用其原生能力（文件搜索、命令执行、代码编辑）
3. **宪法优先** — 每次重要任务开始前，先阅读本文件和项目级规则文件
4. **反插件膨胀** — 95% 的插件和 skill 会迅速沦为垃圾。只保留经过真实生产验证、持续有效的最小技能集。如果一个 skill 不能在实际项目中反复产生价值，就应该被移除而非搁置
5. **前沿追踪，稳定优先** — 持续跟踪 Claude Code、Codex CLI 及顶级开源 Agent 框架的最新机制（全局规则注入方式、权限模型、上下文窗口策略），择其最安全、最稳定的模式融入本协议。拒绝追逐炒作，只采纳经得起验证的演进
6. **第一性原理：上下文管理** — LLM 的本质是将文本转化为高维向量嵌入，经 Transformer 注意力层处理后预测最可能的下一个 token。所有规则设计必须服务于两个目标：① 让注意力机制锁定更精准（结构化、无歧义的指令 = 高信噪比输入） ② 在有限的 Context Window 中做到最优管理（全局规则精简通用，项目规则按需分层，杜绝冗余指令浪费 token）

## 默认执行方式

除非任务极小、风险极低，否则默认按下面的顺序执行：

1. 用一句话说清目标、边界和成功标准
2. 先找最小可行方案，拒绝过度设计
3. 只修改必要文件，避免扩散改动面
4. 用构建、测试、运行结果或明确检查项闭环

## 意图路由

### 场景 A：大型新功能开发 / 核心逻辑重写

**触发条件**：需求涉及新页面、新组件系统、多文件联动、核心业务流程等。

**流程**：

1. **先定义成功标准**
   - 写清楚用户要完成什么、完成后看到什么、用什么方式验证
   - 没有成功标准，不进入实现

2. **CEO Review（产品思考）**
   - 代入 PM/CEO Review 角色
   - 输出：业务价值、用户核心路径、Edge Cases、产品参考矩阵
   - 写入实施计划文档

3. **Eng Review（架构锁定）**
   - 代入首席架构审阅者角色
   - 输出：文件清单、数据流、依赖图、复杂度评估
   - 追加到实施计划文档

4. 🚧 **强制拦截** — 暂停并询问用户："以上产品与技术方案是否通过？"

5. **编码执行** — 按任务清单逐项推进，坚持最小可行实现

6. **局部审查（每完成一个模块后）**
   - 运行构建命令确认无编译错误
   - 检查新增代码是否有 TODO/FIXME/console.log 残留
   - 确认交互闭环：每个按钮/输入都有响应

7. **全局审查（全部完成后）**
   - 代入 QA 角色
   - 逐文件审查代码质量、DRY 违规、错误处理
   - 启动开发服务器，逐页验证交互

### 场景 B：Bug 修复与疑难杂症

**触发条件**：报错日志、功能失效、构建失败。

**流程**：

1. 不急着改代码，先复现并梳理 Bug 触发链路
2. 系统性定位根因，禁止“猜一个修一个”
3. 定位根因 → 修复 → 运行构建命令验证

### 场景 C：前端 UI 微调

**触发条件**：仅涉及颜色、边距、动画、文案。

**流程**：直接定位目标组件文件做手术式修改，不扩散到无关页面或样式层，修改后告知用户确认视觉效果。

### 场景 D：代码重构

**触发条件**：优化代码结构、提取公共组件。

**流程**：

1. 先审查目标代码，并写清哪些行为不能变
2. 小步重构，每步构建验证
3. 重构不能改变业务逻辑

## 质量门禁

### 编码质量检查清单

每次提交代码后自检：

- [ ] **零静默失败** — 每个 catch 块都有用户可见的反馈
- [ ] **状态完整性** — 每个 loading 状态都有对应的 loaded/error 状态
- [ ] **空状态设计** — 每个列表/表格都有空状态提示
- [ ] **交互确认** — 每个按钮点击都有视觉反馈（loading/disabled/动画）
- [ ] **DRY** — 重复超过 3 次的模式应提取为组件/函数
- [ ] **无残留** — 无 console.log、无 TODO、无硬编码路径
- [ ] **类型安全** — 无 `any` 类型（TypeScript 项目），接口定义完整

### 设计质量检查清单

- [ ] **风格一致性** — 遵循项目级设计语言规范
- [ ] **动效克制** — 动画有节制，只用于增强交互体验
- [ ] **响应式** — 所有 grid 布局在窄屏下优雅降级
- [ ] **可访问性** — 所有交互元素有 hover 状态和 focus 样式

## 通用审查命令

以下命令适用于所有 Node.js 项目：

### 构建验证
```bash
npm run build
```

### 代码残留检查
```bash
# 检查 console.log 残留
grep -rn "console.log" --include="*.ts" --include="*.tsx" --include="*.js" --exclude-dir=node_modules

# 检查 TODO/FIXME 残留
grep -rn "TODO\|FIXME\|HACK\|XXX" --include="*.ts" --include="*.tsx" --include="*.js" --exclude-dir=node_modules
```

### 依赖审计
```bash
npm ls --depth=0
```

## 技能库 (Skills)

以下顶层技能通过 `/skill-name` 触发（需安装到对应平台的 skills 目录）：

> **官方源说明**：从现在开始，`gstack` 不再以 Lotus 仓库里的快照为准。Lotus 的全局安装脚本会把 **官方 [garrytan/gstack](https://github.com/garrytan/gstack)** 安装到 `~/.gstack/repos/gstack` 并为支持的平台生成技能。凡是 `gstack` 相关能力，以上游仓库为唯一真源。

> **顶层露出 vs 后台路由**：Lotus 默认只把少数官方 gstack skill 暴露到宿主顶层菜单，供用户手动 `/` 选择：`gstack`、`office-hours`、`plan-ceo-review`、`plan-design-review`、`plan-eng-review`、`design-review`、`review`、`investigate`、`browse`、`qa`、`ship`。其他官方 gstack skill 仍保留在 `~/.gstack/repos/gstack/.agents/skills/` 中，不在顶层菜单显示；当任务语义明显命中时，可在后台按需读取对应 `SKILL.md` 并执行其流程。

**任务级技能**（可作为独立任务执行，兼容所有平台的 `/` 命令）：
1. **/gstack** — 需 gstack 流程时打开总入口。
2. **/anysearch** — 实时搜索、垂直检索、批量搜索和 URL 内容提取。
3. **/test-driven-development** — 写功能修 Bug 前先写失败测试。
4. **/frontend-design** — 做前端页时提升布局视觉交互。
5. **/taste-skill** — 界面显模板时提升审美质感。
6. **/image-2** — 生图改图时生成视觉素材。
7. **/ai-progress-workspace** — 用事件流展示 AI 真实进度。
8. **/web-to-design-md** — 做官网前拆参考生成 design.md。
9. **/debugging-strategies** — 排 Bug 时用假设验证定位问题。
10. **/mini-investigate** — 查小 Bug 时做最小修复。
11. **/security-auditor** — 审安全时查权限依赖合规风险。
12. **/feynman** — 讲概念时用白话解释本质。
13. **/polanyi-tacit** — 读复杂代码时分析隐性约束。
14. **/auto-build** — 验构建时自动装依赖并打包。
15. **/agent-training-loop** — 修 Bug 时循环复现定位修复验证。
16. **/baseline-packager** — 防回归时固化已验证行为。
17. **/conversion-copywriter** — 写营销页时生成转化文案。
18. **/powerup** — 练 AI 编程时走 10 关训练。
19. **/insights** — 复盘习惯时分析摩擦给建议。
20. **/subagent** — 任务可并行时编排子 Agent。
21. **/goal** — 长期任务时管理 Codex 目标。

**会话内技能**（依赖"不中断当前对话"，在对话中直接输入触发词即可，不要用 `/` 命令）：
8. **@btw** — 临时插问时不中断主线回答。
9. **@loop** — 需轮询时会话内定时执行。

> **平台差异说明**：Codex App 中每个 `/` 命令会创建独立任务，因此"会话内技能"不注册为 `/` 命令。在 Codex 中使用这些技能时，直接在对话中输入 `btw，你的问题` 即可，AI 会根据本规则识别并响应。
